# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

pyppetdb is a Python (FastAPI + MongoDB) replacement/middleware for Puppet infrastructure: PuppetDB endpoints, a database-backed Puppet CA, a Puppetserver front-end with catalog caching, a validated Hiera backend (PyHiera), fact-based RBAC, secrets redaction, and a secure job execution engine driven over WebSockets. Docs in `docs/` (mkdocs) — `docs/architecture.md` is the best overview.

## Commands

Dependencies are declared in `pyproject.toml` (direct ones only, with lower bounds) and locked in `uv.lock`; `requirements.txt` is `uv export` output for plain pip and never edited by hand. `uv sync --group dev` creates `.venv` for the current interpreter (3.12, 3.13 and 3.14 are supported and tested in CI); an existing `venv/` from earlier setups keeps working. To bump one package: `uv lock --upgrade-package <name>`, `uv sync`, tests, then re-export `requirements.txt`. Use the project venv (`.venv/bin/python`, or `venv/bin/python` on older checkouts, or `uv run`).

```bash
# Unit tests (no external services needed)
APP_SECRETKEY=ci-test-secret python -m unittest discover tests/unit

# Single test module / case
APP_SECRETKEY=ci-test-secret python -m unittest tests.unit.test_crud_nodes
APP_SECRETKEY=ci-test-secret python -m unittest tests.unit.test_crud_nodes.SomeTestCase.test_something

# Integration tests (require a MongoDB replica set; they self-skip if unreachable)
MONGODB_URL="mongodb://localhost:27017/?replicaSet=rs0" APP_SECRETKEY=ci-test-secret \
  python -m unittest discover tests/integration

# Lint (config in pyproject.toml: ignores E501,W503)
flake8 pyppetdb
```

Tests are stdlib **unittest**, not pytest — do not install or use pytest.

The server runs via the `pyppetdb` console script (`pyppetdb.main:main`). Configuration is entirely environment variables / a `.env` file (pydantic-settings), nested with `_` as delimiter (`app_main_port` → `app.main.port`); list values are JSON strings. `app_secretkey` is required or the process won't start. Full reference: `docs/configuration_reference.md`.

## Architecture

One FastAPI app on a single port; three router groups toggled by config flags and distinguished by URL prefix:

- `/api`, `/oauth` — management REST API (`app_main_enable`)
- `/puppet`, `/puppet-ca` — Puppetserver front-end + Puppet CA (`app_puppet_enable`)
- `/pdb` — PuppetDB command/query endpoints (`app_puppetdb_enable`)

MongoDB **must be a replica set**: change streams drive cache invalidation, inter-instance coordination, and live job logs. Multiple identical replicas share one MongoDB and coordinate over an inter-instance WebSocket mesh.

### Layering

Request flow is controller → crud → MongoDB, with Pydantic models at the boundaries:

- `pyppetdb/controller/` — FastAPI routers, directory structure mirrors URL structure (`controller/api/v1/`, `controller/puppet/v3/`, `controller/puppet_ca/v1/`, `controller/pdb/cmd|query/`, `controller/oauth/`).
- `pyppetdb/crud/` — one class per MongoDB collection (plus `mixins.py` for filtering/sorting/pagination/projection and `common.py` for the base `Crud`). All crud instances are registered with `CrudManager` so `init_all()` creates indexes/watchers.
- `pyppetdb/model/` — Pydantic request/response schemas, file names parallel the crud files.
- `pyppetdb/container.py` — `AppContainer` is the composition root that wires everything (cruds, services, redactors, authorizers). **Adding a collection touches all four places**: model file, crud file, registration in `AppContainer`, controller. It also bootstraps the default `puppet-ca` CA authority/space on startup.
- `pyppetdb/main.py` — settings, logging (structlog), TLS/uvicorn setup with custom protocols that capture client certs (`ca/protocol.py`, subclasses uvicorn's `HttpToolsProtocol` and injects `client_cert_dict` in `on_headers_complete`; the server runs on `uvloop`), app assembly, background workers.

### Subsystems

- `pyppetdb/ca/` — `CAService` implements the CA (signing, revocation, CRLs, secret resolution). CA data lives in MongoDB, so every instance can act as CA. Revocations propagate to the `AuthorizeClientCert` validators via listeners registered in `container.py`.
- `pyppetdb/authorize/` — `AuthorizePyppetDB` (fact-based RBAC: Teams → node-group fact matching) and `AuthorizeClientCert` (mTLS client cert validation against the CA collections, used for `/puppet` and `/pdb`).
- `pyppetdb/ws/` — `WsHub` owns agent WebSocket connections and log-subscription fan-out; `inter_api.py` is the instance-to-instance relay used when a job request lands on a different instance than the one holding the agent connection; `remote_executor.py` speaks the agent job protocol. `pyppetdb/jobs/service.py` handles job scheduling/expiry/dispatch.
- `pyppetdb/pdb/query/` — the PuppetDB query engine behind `/pdb/query/v4`. `entities.py` maps each PuppetDB entity onto the MongoDB documents via a `$project` whose keys are the PuppetDB column names, `ast.py` parses/compiles the AST query language, `engine.py` builds and runs the aggregation pipeline, `matcher.py` is the Python-side evaluator for entities expanded in Python (`fact-paths`, `fact-contents`). That expansion (`QueryEngine._run_python`) streams the cursor in `PYTHON_BATCH_SIZE` batches through `asyncio.to_thread`, checks the query deadline per document (an `asyncio.timeout` cannot interrupt synchronous code — an unfiltered `fact-contents` query over 10k nodes used to freeze the whole instance for half an hour), stops reading once `offset + limit` rows are in hand unless `include_total` or aggregation need everything — with `order_by` only when it starts with a column stored in the unique document `id` (`certname`), in which case the cursor is sorted by `id` (`_document_order`, `allow_disk_use`) so the rows of the documents read so far are a prefix of the global order — and projects only `facts.<name>` for the names the filter allows. Entities with a `path_source` (`fact-contents`) resolve those names first: `_path_node` reduces the compiled match to its `name`/`path` clauses (dropping every other clause and every `$nor`, so it can only over-match), `_fact_path_candidates` evaluates that against the `distinct` of `fact_paths`, and the matching entries become both the projected names and, up to `MAX_PATH_PREFILTER`, a `fact_paths: {$in}` pre-filter; no matching path means no document is read. The exact match still runs per row. This relies on `fact_paths` being present on every node — nodes stored before the field existed are invisible to path- and name-filtered `fact-contents` queries until their next fact upload. `fact-paths` does not walk documents at all: every fact write (`CrudNodes._with_facts_index`) also stores `fact_paths`, the node's sorted unique leaf paths as compact JSON strings `[path, type]` (`build_fact_paths`), and entities with a `distinct_source` expand the result of `collection.distinct` on that field (a `DISTINCT_SCAN` on `idx_fact_paths`, 16 s → milliseconds). Strings, not `{p, t}` sub-documents: a node-group-scoped distinct over sub-documents is 7–14× slower. `/api/v1/nodes/_distinct_fact_names` reads the same field — unscoped via `distinct`, scoped via `$match` → `$group` on the whole array (nodes with identical fact structure collapse) → `$unwind` → `$group`, because `(node_groups, fact_paths)` cannot share an index (parallel arrays) — and returns dotted leaf names without array indices. Nodes written before the field existed contribute nothing until their next fact upload; there is no backfill. Because the compiled `$match` uses column names it must sit behind the `$project`; `engine.py` therefore derives a **document pre-filter** (storage paths, runs first, uses the indexes) and an **element filter** (pushed into the projection's `$filter` so arrays are narrowed before `$unwind`) from it. Both are derived only from positive-polarity clauses so they can only over-match — never drop a row the full `$match` would keep. `app_puppetdb_querySource` switches queries between this engine and an upstream OpenVoxDB; commands are always stored locally and forwarded upstream when `app_puppetdb_serverurl` is set. The HTTP layer mirrors upstream's route tree and parameter rules (`controller/pdb/query/v4/__init__.py`): `ENTITY_ROUTES` is generated from `_fact_routes`/`_resource_routes`/`_report_routes`/`_catalog_routes`/`_factset_routes` so every nested child route (`/nodes/<n>/facts/<f>/<v>`, `/environments/<e>/reports/<h>/logs`, `/producers/<p>/catalogs/<n>/resources/<t>/<title>`, ...) exists with the same implicit clauses, parent check (`Route.parent` → 404 JSON `No information is known about <label> <id>`, checked with a one-row `extract` on the parent entity) and parameter spec as upstream; `pdb/query/params.py` holds the per-endpoint allow-lists (`validate_params`, unknown → 400 `Unsupported query parameter`), the float `timeout`, `explain=analyze` (MongoDB `explain` of the real pipeline via `QueryEngine.explain`), the `distinct_*` validation and `has_active_criterion`. Listings of certname-bearing entities pass `restrict_active=True` and the engine merges `["=", "node_state", "active"]` unless the query already mentions `node_state`/`["node", "active"]` anywhere (upstream walks the whole tree, subqueries included); `reports`, `events`, `catalogs` and the single-object routes are never restricted, the root endpoint restricts everything except `fact_paths`/`environments`/`packages`. `include_facts_expiration`/`include_package_inventory` add non-projected columns (`extra_columns`, listings only, upstream ignores the flags on single routes). `distinct_resources` inserts `_distinct_event_stages` behind a prefilter reduced to the partition keys (`node_id`, `latest`) — the user's filter must run *after* picking the latest event per `(certname, resource, property, name)`, ties included, and event counts on that path count events, not identities (`summary_stages(distinct=True)`). Conformance corpus and coverage tool in `tests/conformance/`; the diff tool resolves `{hash}`, `{environment}` and `{producer}` per target from the node itself and pairs tied rows by full content.
- `pyppetdb/hiera/` — PyHiera integration. Key models come from static plugins (Python modules loaded via `importlib` from `app_main_hiera_keyModels`) or dynamic JSON-schema-like definitions stored in MongoDB (`hiera/schema_model_factory.py`). `pyppetdb_dummy_plugin/` is the example plugin package used by tests.
- `pyppetdb/pdb/ingest/queue.py` — `IngestQueue`, a bounded background work queue created in `AppContainer` and used by `/pdb/cmd/v1`. One command becomes one queued job; everything touching MongoDB runs on its workers, never on the request path. Jobs enforce the Puppet-run order per node — `replace_catalog` is discarded when the node has no facts, `store_report` when it has no catalog (`CrudNodes.get_ingest_state`). When full the endpoint blocks up to `app_puppetdb_writeQueueWaitTimeout` for a free slot (`IngestQueue.enqueue`, woken by the workers after every dequeue) and only then answers 503 with `Retry-After` — a rejected `store_report` is lost, because Puppet Server does not spool commands. CPU-bound work on the command path (gzip/JSON decode, catalog and report normalisation, building the resource documents, the history model) runs in `asyncio.to_thread` so it does not stall the event loop that all queue workers share. Sized via `app_puppetdb_writeQueueSize` (memory) and `app_puppetdb_writeQueueWorkers` (MongoDB concurrency); depth and counters are reported under `/status/v1/services`. Each queued job may carry an optional **completion future** (`IngestQueue.enqueue(..., completions=[...])`, created with `IngestQueue.completion()`), which the worker resolves after the job ran — with its exception when it failed; that is what `secondsToWaitForCompletion` on `/pdb/cmd/v1` awaits (behind `asyncio.shield`, so a timeout never cancels the future the worker is about to settle), and it covers only the local job, never the proxied upstream one. The endpoint validates the request like OpenVoxDB's `http/command.clj` before anything is queued: parameter set, required parameters, command names with `_`/space equivalence, per-command minimum versions, the old body-only request format, `Content-Type`/`Content-Encoding` (415) and `app_puppetdb_maxCommandSize` (413).
- `replace_catalog` answers two separate questions from `CrudNodes.get_ingest_state`: the **content hash** (resources + edges, `catalog_content_hash`, 3 ms per catalog) decides whether resources and edges are rewritten — the daily cache-TTL recompile produces a new uuid with identical content, and rewriting 1000 documents for it costs 40 ms, so the hash pays for itself once one compile in fourteen is unchanged; the **`catalog_uuid`** decides whether a history entry is written (once per compile, keyed by the uuid, so a Puppet Server retry neither duplicates it nor fails). On the unchanged-content path the per-compile metadata (`transaction_uuid`, `version`, `hash`, `producer_timestamp`, ...) is still `$set` via `update_catalog_metadata`, and `change_catalog` is still updated so `catalog_timestamp` keeps PuppetDB's "last received" semantics; the history entry is **not** written again — it is keyed by the uuid, so a second insert would raise `DuplicateResource` and fail the whole job (that is what a Puppet Server retry looked like before). The check runs inside the background task, never on the request path.
- Query-path performance rules that are easy to break: when a filter pins the fact `name` to constants, `build_pinned_keys` replaces `$objectToArray` with a literal `[{k, v: "$facts.<name>"}]` array so nothing is unwound; the exact `$match` still runs behind it, so an over-broad key set stays correct.
- Query-path performance rules that are easy to break: the compiled `$match` is written in column names and therefore runs *after* the `$project`, so anything that rewrites values (date formatting) must come after it, never inside it. `build_projection` emits only `projected=True` columns plus whatever the filter/`order_by` needs, and the helpers are removed again with `$unset`; `Entity` has no `projection()` method any more. Rows leave the engine as they come out of MongoDB — timestamps stay `datetime`, missing columns are nulled by a `$set`/`$ifNull` stage at the very **end** of the pipeline, behind `$match` and paging (in front of the `$match` it turns renamed columns into computed ones, which stops MongoDB from pushing the `$match` below the `$project`/`$unwind` — a 10k-clause subquery `$or` went from 138 s to 2100 s that way) — and `PdbJSONResponse` serialises with `orjson` (`OPT_UTC_Z|OPT_NAIVE_UTC` reproduces PuppetDB's `Z` timestamps natively); the Python json encoder was a third of the server's CPU. `fact-names`, `environments` and `producers` carry a `distinct_field` and are served by `collection.distinct` (a `DISTINCT_SCAN`, no documents examined) whenever the query extracts at most that one column, the filter maps to an **exact** pre-filter on it (passed to `distinct`) and the only function is a `count`, which is then the number of values (`_distinct_eligible`); `environments/production` went from 2.7 ms of scanning a third of all node documents to a single index seek. `$lookup` stages whose output field nothing downstream reads are dropped before every execution (`_prune_lookups`; kept if anything references `$$ROOT`/`$$CURRENT`) — catalogs used to join ~2000 resources and edges per node even for `extract certname`, which made every `/catalogs/<n>/…` parent check cost 5.7 ms. Parent checks go through `QueryEngine.exists`, a `find_one` on the exact pre-filter for document-row entities. `decode_fact_path` is backed by an LRU cache (`FACT_PATH_CACHE_SIZE`), since the same few hundred encoded paths are decoded on every `fact-paths` request. there is no aggregate cache any more.
- `events` live in their own collection `nodes_events` (one document per event, flat columns, `build_event_documents` in `helpers/puppetdb.py`), written by `_job_store_report` from the **redacted** report dict that `CrudNodesReports.create_latest` returns alongside the latest flag — never from the wire payload, which has string timestamps and unredacted values. The report keeps its embedded copy for the `reports` entity. `latest` mirrors `report.latest`: a new report becomes the latest only when its `producer_timestamp` (falling back to `end_time`) is **strictly** newer than the stored latest's — upstream's `(.after producer_timestamp latest-ts)`, so equal timestamps keep the old report — and then `CrudNodesEvents.set_latest(node, False)` runs before its events are inserted with `latest: True`; a report that is not the latest still updates `change_last` on the node but none of its report-derived fields (`report`, `change_report`, `environment`, `producer`, `producer_timestamp`), because upstream derives those from `reports_latest`. `event-counts` follow upstream's `query/event_counts.clj` literally: `count_by=resource` simply counts events per bucket and status (no de-duplication — six stored reports of a node yield six times the counts, and upstream agrees), `count_by=certname` first collapses `(certname, status, corrective_change, <bucket fields>)`; both run as `$group` stages behind `QueryEngine.group`, served from the covering index `idx_latest_counts` (`latest, status, node_id, resource_type, resource_title, containing_class, corrective_change`) whenever the filter pins `latest_report?`, and `QueryEngine.group` drops the `$project`/`$match` pair and rewrites `$<column>` references to storage paths (`_rewrite_to_storage`) when the filter is exact at row level, which is what makes the covered plan possible — a `$project` in front of the `$group` forces a fetch. When such a filter leaves `latest` open, `_covering_prefilter` adds `latest: {$in: [true, false]}` (declared on the entity as `covering_index`, a unit test keeps it equal to the crud's `idx_latest_counts`) so a status-only or unfiltered count still rides the covering index instead of fetching every event (481 → 253 ms, 352 → 167 ms); it is only applied when every pre-filter field is in that index, and it relies on every event carrying a boolean `latest`, which `build_event_documents` guarantees. A re-sent report (same `report.hash`, e.g. a Puppet Server retry) is skipped entirely (`CrudNodesReports.hash_exists`), as upstream does. `containing_class` is precomputed at ingest (`containing_class()`), the same rule as the old `$reduce`. Indexes end in `timestamp` so `order_by timestamp` streams from the index; the diff tool's six-key ordering has no index and sorts 400k documents per page, which is the one events case still slower than OpenVoxDB. Every cascade that touches resources/edges (node delete, `disabled` propagation, placement update) touches events too. Both `nodes_reports` and `nodes_events` expire through a TTL index on `created`, which every report write path sets to the receive time (`id`); reports stored before that field existed never expire, there is no backfill.
- `node_state` on `reports`/`events` is **materialised**: `nodes_reports` and `nodes_events` documents carry a top-level `disabled` mirroring `nodes.disabled`, so the column pre-filters like any other instead of expanding into a cross-collection subquery. Every write path that touches `nodes.disabled` propagates it with a conditional `update_many` (`CrudNodesReports.set_node_disabled`, filtered on `disabled: {$ne: <new>}`), so the steady-state Puppet run costs one index seek and no writes. Both `/pdb` command jobs (`_propagate_node_state`, reached from `_job_update_node` *and* `_job_replace_facts`, which bypasses it) and the `/api` node update must call it. Documents predating the field read as `active`, which is the correct default, so no migration is needed.
- Query guards, all configurable and all upstream-derived: `app_puppetdb_maxQueryDepth` (AST nesting, corpus maximum is 12), `app_puppetdb_maxSubqueryDepth` (round trips, corpus maximum is 2) and `app_puppetdb_queryTimeout`/`queryTimeoutMax` with the `?timeout=` parameter. `check_depth` recurses with a **countdown budget**, so it never descends deeper than the limit it enforces — computing the full depth first and comparing afterwards would blow the stack on exactly the queries it exists to reject. With `maxQueryDepth` disabled that budget is gone, so the call is wrapped in a `RecursionError` guard that still answers 400. Subquery results are de-duplicated inside the aggregation (`$group` before `$limit`), so `SUBQUERY_LIMIT` counts distinct values rather than raw rows. Subqueries are narrowed by their outer `and`: `FilterCompiler` collects the string values that `=`/`in [array]` conjuncts pin a column to (`_conjunct_pins`, intersected down the tree, up to `MAX_PINNED_VALUES`) and appends them to any `in`/`subquery` on that column as `["=", <remote column>, v]` — sound under `or`/`not` inside the `and`, because the clause is only ever evaluated for rows carrying a pinned value, but never taken from an `or` sibling, and only when the remote column is a plain string column (`_pinnable`). `facts … and certname = X and subquery resources` went from 60 ms to 4 ms that way. A single-column `select_facts` on a document-level column (`certname`, `environment`) whose filter pins `name` by `and` to at most `MAX_PINNED_KEYS` plain names (`SAFE_KEY`, no dots) and is otherwise exact at document level is the question "which nodes carry this fact", so `QueryEngine._select_fact_documents` answers it with `[$match facts_index.p = <name> and facts.<name> $exists, $group $<path>, $limit]` instead of unwinding every fact (`name=kernel` over 10k nodes: 90 → 46 ms); every other shape falls through to `_select_distinct`/`_run_mongo`. A single-column subquery on a document-rows entity whose pre-filter is **exact** skips the projection entirely and runs `[$match <prefilter>, $group {_id: $<storage path>}, $limit]` (`QueryEngine._select_distinct`), which MongoDB 8 answers with a `DISTINCT_SCAN` when an index ends in the grouped field — that is why every lookup index on `nodes_resources` ends in `node_id` (`(type, node_id)`, `(type, title, node_id)`) and the certname index is `(node_id, type, title, disabled)` — the trailing `disabled` lets the `node_state` restriction of every listing be checked on the index keys, so a deep `offset` skips index entries instead of fetching every skipped document (a 325k offset went from 640 to 280 ms) —, which also streams the outer page in `certname, type, title` order through a 10k-value `$in` instead of sorting 10M documents (`select_resources type=File` went from 3.5 s to 80 ms, the outer page from 12 s to 30 ms). A multi-column `in` never compiles to a `$or` of tuple clauses (10k branches were evaluated per document, 13 s a page): `_compile_in` emits one over-matching `$in` per column for the pre-filter plus an internal `__tuple_in__` node (`TUPLE_IN`), which `_mongo_safe` turns into an `$addFields` helper (`__tuple_<n>`, an object keyed `"0"`, `"1"`, … so array-valued columns cannot match element-wise) followed by a set-based `$in` — every walker over the compiled match (`_prefilter_node`, `_pinned_node`, `_element_node`, `_collect_match_columns`, `matcher.matches`) has to know the node. `CrudMongo._sync_index` migrates renamed *and* re-keyed indexes (codes 85 and 86, all conflicts in one pass) and compares key specs **order-sensitively** — `(node_id, type, title)` and `(type, title, node_id)` are different indexes that a plain dict comparison called equal, which silently dropped the freshly built one. List responses of entities answered by `_run_mongo` are **streamed**: `QueryEngine.run(..., stream=True)` returns a `RowStream` whose first `STREAM_BATCH_SIZE` batch is fetched inside `_guarded` (so query errors and timeouts still become proper status codes), the rest is pulled from the cursor while `stream_response` writes the JSON array chunk by chunk (byte-identical to the buffered `PdbJSONResponse`/pretty output, a unit test compares them); `include_total` counts up front. An error after the first chunk can only abort the connection. `_stream_body` checks `request.is_disconnected()` per batch and closes the cursor — uvicorn silently drops writes to a closed connection, so without that check an aborted client keeps the instance reading the whole cursor. Streaming large results with the default glibc allocator grows RSS across requests (motor decodes BSON in its worker threads, each with its own malloc arena: 1.67M rows three times took the instance from 1.0 to 1.6 GB); with `MALLOC_ARENA_MAX=2` it stays flat at ~250 MB, so deployments should set it. `app_puppetdb_maxPageSize` bounds only the paths that still materialise (Python-expanded entities, `distinct`-served entities, single routes): `_apply_page_cap` asks for `limit + 1` rows and `_within_cap` answers 400 (`page_too_large`) when that extra row shows up — never truncate silently again; `event-counts`/`aggregate-event-counts` no longer page through events at all — `QueryEngine.group` runs the compiled filter (pre-filter, projection, `$match`) and appends the stages from `event_counts.summary_stages`: a distinct `$group` over (bucket, status, count-by identity) followed by the bucket sums, or on the single-report fast path one `$group` summing the first flags; only `counts_filter` and the aggregate totals stay in Python. MongoDB cannot continue a sort that an index delivers only partly (PostgreSQL's incremental sort), so an `order_by` whose leading keys match an index prefix but not the whole index — typical for tie-breakers such as `certname, timestamp, resource_type, resource_title, …` — used to blocking-sort every matching row per page. `_incremental_prefix` detects that case (scalar column types only, `ORDERABLE_TYPES`, all order columns in the output): the pipeline sorts on the prefix only, carries no `$skip`/`$limit`, and `_incremental_rows` sorts each group of equal prefix in Python with BSON type order (`_bson_order`), applies offset/limit and stops as soon as the page is complete. With an ascending prefix, a pre-filter that the prefix index covers and an exact match, `_incremental_boundary` first scans the covered prefix keys to find the group that contains row `offset` and restricts the real query to it and everything after (`_boundary_condition`; never with a `null` boundary, because MongoDB's comparison operators are type-bracketed). Both cursors set `batchSize` — without it every `getMore` fills 16 MB (~20k events) although only a page is needed, which alone tripled the page time. 10 pages of 5000 events in the diff tool's 7-key order: 16.5 s → 3.1 s (OpenVoxDB 4.3 s). The incremental sort is skipped when the pre-filter pins the leading key of an index to a single value (`_single_value_fields`, e.g. `node_id = X`): such a result is small, and a blocking top-k sort that only projects the page beats streaming and projecting every row of it (one node's resources ordered by `type, title desc`: 32 → 5 ms). `aggregate-event-counts` without a `counts_filter` sums the per-subject counts in MongoDB (`event_counts.aggregate_stages`) instead of shipping one row per certname to Python. `_run_mongo` hoists `$sort`/`$skip`/`$limit` in front of the `$project` whenever the match is exact at row level (`rows_exact`: exact pre-filter, no element filter or pinned keys, every filtered column document-level per `_document_level`) — `node_state` counts as document-level through its `disabled` pre-filter (`_document_prefilter_path`); before that the implicit active restriction of every listing silently disabled the hoisting, so each page pushed all skipped rows through `$project` (67 pages of 5000 resources: 56.8 s, now 13.8 s; OpenVoxDB 30 s). Pushing `$skip` into the query layer makes MongoDB's multi-planner run every candidate through the whole offset whenever it replans (every new offset can trigger that), so a useless candidate index is expensive. `nodes.idx_disabled` must stay a **full** index even so: a partial one (`disabled: true` only) removed it as a paging candidate but also turned every active count (`nodes_active_count`, `include_total` on `/nodes`) into a scan of 79 KB node documents (3.8 → 13 ms); keeping `$skip` behind the `$match` already bounds its trial. Exported resources have two small partial indexes (`exported: true` only, 18 MB for 400k of 10M resources): `idx_exported_type` `(type, title, node_id, disabled)` serves the collector queries Puppet Server sends on every compile (2.35 s → 70 ms raw), `idx_exported_node_id` `(node_id, type, title, disabled)` the exported resources of given nodes (3.1 s → 128 ms); the compiled pre-filter for `["=", "exported", true]` is the literal `{exported: true}` the partial filter needs. `nodes.idx_disabled_report_status` lets the active status grouping skip fetching the 79 KB node documents (`nodes_group_by_status` 45 → 16 ms). Optional node data (`package_inventory`, `catalog_inputs`) has partial indexes on `(id, disabled)` whose filter is repeated literally in the first `$match` of `packages`/`catalog-inputs`/`catalog-input-contents`, together with an always-true `id: {$type: "string"}`: MongoDB only considers an index when the query constrains one of its **keys**, so without that clause the partial index is ignored and an empty result still scanned every node (31–37 → 2 ms; a unit test keeps stages and partial filters in sync). `_sync_index` drops and recreates a same-name index whenever `create_indexes` reports a conflict (85/86), so key *and* option changes (partial filters) migrate on startup. For the same reason a filtered hoisted page with an `offset` normally does **not** push `$skip` into the query layer: the head ends in `$limit: offset + limit` and `$skip` sits behind the post-projection `$match` (`_skip_behind_match`; a `$match` is the one stage MongoDB cannot move a `$skip` across), so the trial stops after 101 rows. `$skip` is only pushed down when there is no filter, or when `offset >= DEEP_OFFSET` **and** an index starting with the sort keys contains every pre-filter field (`_skips_on_index_keys`, index list cached for `INDEX_KEYS_TTL`, partial indexes never count) — only then does MongoDB skip on index keys without fetching (a 325k offset: 280 ms against 1.5 s behind the `$match`). Without that condition a pushed `$skip` just lengthens every replan: a page past the end of `/nodes` filtered on `report_timestamp` took 900 ms because both candidates had to run to EOF, for unwound entities too — before events had their own collection this alone took an events page from 2.4 s to 0.9 s. `~>` follows upstream's two implementations: on `fact-paths` every regex must match its path element **in full** (`re.fullmatch`, upstream joins the array into one `^el#~el$` regex over the encoded path), on `fact-contents` each element is an unanchored `re.search` (upstream's `path-array` match) — the compiler picks `__regex_array_full__` or `__regex_array__` per entity; `~` stays an unanchored search everywhere.
- Fact queries ride on `facts_index`, a flat `[{p, v?}]` array written next to `facts` on every fact write (`build_facts_index` in `helpers/puppetdb.py`, applied in `CrudNodes._with_facts_index` so no write path can skip it) and covered by the single compound multikey index `idx_facts_index` on `(facts_index.p, facts_index.v)`. Every top-level fact name is always present (that is what `fact-names` reads) and costs exactly one entry: `{p, v}` when the value is an indexable scalar, a bare `{p}` when it is structured, denied or oversized; deeper paths and list elements add further `{p, v}` entries at an indexable path (`app_main_facts_indexDepth`, `app_main_facts_indexMaxValueLen`, `app_main_facts_indexDeny`), lists not consuming a depth level so array facts match MongoDB's implicit array traversal. An indexable fact equality compiles to **both** forms — the `$elemMatch` on `facts_index` (what the generic index serves) *and* the direct `facts.<path>` predicate (O(1) residual, plus any dedicated `app_main_facts_index` index); emitting only one of them is measurably slower. Soundness rule: because a pre-filter may only over-match, the engine emits the `$elemMatch` only when its own indexability check — identical to the ingest rule, fed from the config through the `QueryEngine` constructor, never read globally — guarantees the entry was written; everything else falls back to the direct predicate. There is no backfill, so changing the config only takes effect on the next Puppet run of a node.
- Secrets redaction: `NodesSecretsRedactor` and the catalog/report redactors (`NodesCatalogsRedactor`, `NodesReportsRedactor` in `crud/nodes_*`) redact at **read time** only — inside `CrudNodesReports.get/search` and `CrudNodesCatalogs.get/search`, which only the `/api` routes call. MongoDB stores everything as received: `/puppet` serves unredacted catalogs to agents, `/pdb/query/v4` is deliberately exempt (PuppetDB compatibility for existing tools, so reports, events and resources come back verbatim), and facts are never redacted. Job logs live on the agent and are redacted when the chunks arrive. The node document only carries a **summary** of its latest report (`report_summary` drops `logs` and `resources`, 18.6 of 19.4 KB, which the node queries never need); `/api/v1/nodes` adds them back from the latest `nodes_reports` document whenever `report`, `report.logs` or `report.resources` is requested (`ControllerApiV1Nodes._attach_report_details` → `CrudNodesReports.latest_details`, one `$in` query per page, redacted) — before that the node's copy went out unredacted. Nodes stored earlier still carry the full copy until their next report, but the API always replaces it. Never redact in a write path again — it would silently redact the PuppetDB API too, and a secret added later would stay in the clear for the whole retention period. Catalog history stores the resources/edges as `catalog_content`, a zlib+Fernet blob from `NodesDataProtector.encrypt_obj` (the catalog cache's encoding), next to `catalog_metadata()` as plain fields for indexes and `fields=` selection; `CrudNodesCatalogs._inflate` merges the blob back and redacts when `catalog` is requested. Old history documents without the blob still read fine.

### Testing conventions

- `tests/unit/` uses mocks throughout; file names map to source (`test_crud_nodes.py` → `pyppetdb/crud/nodes.py`, `test_api_v1_*` → `controller/api/v1/*`).
- `tests/integration/` boots the real app via `IntegrationTestBase` (`tests/integration/base.py`) with a real MongoDB (`pyppetdb_test` database) and FastAPI `TestClient`; skips itself when MongoDB is unreachable.

## Code style

- No `#` comments and no docstrings — write self-explanatory code. Keep the Apache 2.0 license header at the top of every source file (copy it from any existing file when creating new ones).
- flake8 with `E501,W503` ignored is the only linter; there is no formatter config, but the codebase follows Black-style formatting.
